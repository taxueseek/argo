# 多语言垂直源扩展（2026-09-21）

> 本轮：接 14 个本地语言新闻源 + 把「语言」接成选源的一等信号。
> 仓库：`~/.agents/skills/argo`（argo-search 2.8.9，本地领先 origin 21 个提交）

---

## 一、重新定义问题

用户的问题是「还有没有优质的垂直搜索源」。按字面做，就是再拉一批 API 填进
`engines/specs/`。但先做量化盘点后发现，**源的数量不是瓶颈**：

| 维度 | 现状（本轮之前） |
|---|---|
| 源总数 | 239 |
| 覆盖语言（有**本地一手**源的） | zh、en、ja、de、fr —— 5 种 |
| 零本地源的语言 | ko、ru、ar、es、pt、it、nl、pl、th、vi、id、tr、he、cs… |
| 18 语言能力矩阵（2026-09-10 实测 1044 次调用） | es 12 个可用引擎 / th 仅 3 个 |

`kor_law` 是当时**唯一的韩语源**（`ENGINE_LANGS` 表里 ko 只有它一条）。俄语、
阿语、西语、葡语、越南语、泰语、印尼语、土耳其语、荷兰语、希伯来语、捷克语
全部为 0——这些语言的查询只能落到通用源（wikipedia / anysearch / tavily / exa），
拿到的是英文或机器转述的内容。

**所以真问题不是「源不够」，是「非中英日的语言没有一手通道」**。第一性分解：

```
非中英日查询的检索质量 = P(该语言有本地源) × P(路由能选中它) × P(结果相关)
                              ↑ L1 源层（≈0）      ↑ L2 接线层（缺）     ↑ L3 判定层（已有）
```

L3（噪声门 / 结果侧语言判定）在 2026-09-10 那批已经做完；本轮要补 L1 和 L2。

**只做 L1 等于没做**——实测（本轮接线前）：

```
$ argo search "오늘 뉴스" --plan-only        → 域 general_search，combo=[anysearch, local_bing]
$ argo search "новости сегодня" --plan-only  → 域 general_search，combo=[anysearch, local_bing]
$ argo search "noticias de hoy" --plan-only  → 域 general_search，combo=[anysearch, local_bing]
```

接了源，路由选不中，源就是死的。

## 三、接线：把「语言」接成选源的一等信号

新源声明了 `langs` 还不够——**预算窗口只放得下 2 个源**（fast 档 `budget=2`），
语言源排在窗口外就永远不参与自动路由。

### 3.1 三层改动

**① 新族 `world_news`（本地新闻流）**

不塞进 `hot_trending`：同族 `max_per_family=2`，14 个语言源挤在一起会互相顶掉。
新族同时登记进 `_REFILL_EXCLUDED_FAMILIES`（实时流不参与通用 combo 回填，同
`hot_trending` 的理由）。

**② `_filter_lang_bound_family`：族内按查询语言互斥**

语言绑定族的语义是「每个源服务一种语言」，所以选源的第一判据是**查询语言**，
不是 priority：匹配的留下，**不匹配的一律摘除**。

这里刻意不走 `engines_demote_for_lang` 的「移尾降级」——那条路径处理的是
「同一份内容的不同语言版本」，这条处理的是「完全不同的国家与语言」。移尾方案
在 deep 档（不截断预算）会露馅：实测韩语查询连跑 elpais / tass / aljazeera 等
16 个源，白付网络与配额，拿回的还都是别国语言的内容。摘除后 deep 档只剩
`[anysearch, yna, local_bing, local_duckduckgo]`。

摘除的代价是「语言判定失误时拿不到该语言源」，但 combo 里始终有语言中立的
`anysearch` 兜底，不会零结果；判定不确定（mixed/other/空）时整个族不动。
域 patterns 误伤（英文 `world news` 命中过该域）时也会退化成整族摘除——
所以英文那条 pattern 已从域声明里删掉，英文国际新闻归 `intl_news_flash`。

**③ `_lang_must_keep`：语言绑定源优先于通用 SERP 兜底**

这是让源真正进窗口的一步。此前 ko 查询的 `must_keep` 是 `local_bing`（通用
SERP），budget=2 下把 yna 挤出窗口。现在语言绑定的源优先——韩语新闻查询里，
韩联社是该语言的唯一一手通道，`local_bing` 只是二手转述。

### 3.2 两处语言判定缺口的补丁

**语系标签 → 具体语言**（`_SCRIPT_FAMILY_LANGS`）：`lang_detect` 对没有足够
特征的文本只给到书写系统——`новости сегодня` 返回 `cyrillic`，而 tass 声明的
是 `ru`，两边对不上就永远选不中。展开是单向的（查询给语系 → 认该语系下的
具体语言源），反向不展开，防「zh 查询用日文源」串味。

**拉丁语言实词兜底**（`_LANG_HINT_WORDS`）：拉丁字母语言共享字母表，靠码位
分不开（`noticias de hoy` 判成 en、`berita hari ini` 判成 en、`tin tức` 判成
latin）。用该语言的新闻类实词做兜底，**只在语言判定给不出具体语种时生效**，
不覆盖 ko/ja/zh 这类明确判定。

### 3.3 断掉自适应学习的饿死循环

接线完成、路由验证通过之后，跑过一次**真实搜索**，`오늘 뉴스` 的 combo 立刻
从 `[anysearch, yna]` 退化成 `[anysearch, local_bing]`。

根因不是本次改动失效，而是**自适应学习把新源饿死**：anysearch 先返回并触发
early-stop，语言源拿不到贡献分 → 分数低于 0.3 的过滤阈值 → 被 learner 摘出
combo → 下次更不可能被选中。源还在 `enabled` 里，只是路由看不见它了。

修法：把 `world_news` 加入 `route._VERTICAL_PROTECT`（与 `zhihu_content`
当年那笔账同一个机制）。这对新接入的垂直族是**通用风险**——接进来只是第一步，
还要防它被「历史用量少 → 分低 → 更不被用」的回路吃掉。`world_news` 尤其严重：
每个源服务一种语言、族内无替代，被摘掉即该语言通道消失。

### 4.2 端到端（真实请求）

```
$ argo search "noticias de hoy"
  域 world_news · 引擎 [elpais, anysearch]
  1. Sorpresas de un convento de clausura: de la dinastía Ming a ...   (elpais)
  2. La jornada de 35 horas avanza en la administración autonómica ... (elpais)
```

`elpais` 的结果排在第 1 位——西语查询拿到了西语一手报道，而不是英文源转述。

**但要如实说明边界**：语言源被选中、被执行（`engines_used` 里能看到它），
最终排序仍走五维精排。对 `오늘 뉴스` / `ข่าววันนี้` / `חדשות היום` 这类
「无主题的最新流」查询，anysearch 的搜索结果在相关性维度上往往高于热榜源的
最新条目（后者不按 query 过滤，是设计如此），于是 top-N 可能全由 anysearch
提供。实测这四个语言查询的 `engines_used` 都含对应本地源，但结果来源只有
anysearch。

这不是缺陷——热榜源的语义就是「此刻的最近条目」，不是「按 query 检索」——
但意味着**本地源的价值目前主要体现在「查询命中该语言时它在场且被执行」，
而不是「它的条目必然出现在前几条」**。要让最新流条目优先展示，需要动融合层
的源多样性策略（属下一批）。

单源质量实测（同日，绕过融合）：

```
$ argo search "오늘 뉴스"  --engine yna      → 5 条，带发布时间（2026-09-21 15:31 +0900）
$ argo search "ข่าววันนี้" --engine matichon → 5 条泰语新闻
```
